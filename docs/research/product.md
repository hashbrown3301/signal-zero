# iTantra product and UX research — phase 1, read-only

Date: 2026-10-01. Scope: actual `Upgradation` UI/code and primary competitor documentation. No UI/code was changed, no device/native test was run, and no competitor app was installed. Public documents were fetched through the managed environment's configured proxy after reading the cloud-runtime skill/network reference and checking current enforced unrestricted HTTP policy. Downloaded text evidence is in `/workspace/scratch/product-primary/`.

## Recommendation

Build four connected capabilities: **review the source before it leaves; check important details before speech plays; reuse manually reviewed exact phrases without the translation model; recover through typing, retry and replay.** They address errors and resource limitations observed in this app. They are not four claims of worldwide novelty. Typed input, phrasebooks, replay and offline conversations already exist elsewhere; the useful proposition is their integration into an offline ten-language Indian conversation workflow with clear control and failure states.

## Actual iTantra product gaps

| Observed gap | Actual implementation evidence | User impact |
| --- | --- | --- |
| Recognized source is automatically sent or played with no review/edit step | `SessionManager.kt:318–380`: release calls `listener.finish()`, then `handleSpeech`; its text is immediately queued in Solo or encoded/sent over the link. | A misrecognized name, number or request reaches the receiver before the speaker can correct it. |
| Hold gesture cancellation currently follows the send-on-release path | `HoldToTalkButton.kt:90–98`: result of `tryAwaitRelease()` is ignored and `end()` runs even when release was cancelled. | A cancelled gesture can submit unintended speech. A distinct cancel callback belongs in the same source-control workflow. |
| Translation quality issues have no user-controlled speech gate | `SessionManager.kt:459–480` translates then immediately prepares/plays audio. The current benchmark flags name/destination and quantity-wording problems even when all digit groups match (`docs/CURRENT_APP_BENCHMARKS.md:125–144`). | Voice playback can communicate an incorrect critical detail confidently. Deterministic checks can flag some differences, but cannot certify semantics. |
| No typed route if microphone permission is denied, speech is noisy, or recognition cannot load | `TalkScreen.kt:85–176` exposes hold-to-talk, leave, voice installation and Solo actions only; denied mic produces a notice. MainScreen wiring has no typed callback. | The conversation stalls even when users could type. Typing removes STT/microphone dependence; it does not make the large translation model work on an unsupported phone. |
| Transcript taps only open timing details; no retry/replay/edit/save actions | `TalkScreen.kt:355–450`, especially click action at 374. Failures show explanations, but no retry action. | People must record again after recoverable failures or cannot replay something missed. |
| No retained exact phrase library; ending a session clears the visible message state | `MainViewModel.kt:470–479`; there is no phrase persistence model in the audited tree. | Common requests must be generated repeatedly; unsupported low-RAM phones have no model-independent cross-language fallback. |
| Product readiness is not enough for low-RAM translation | Current report documents ~1.91 GiB cloud translation peak RSS and a 64-bit/4-GB-nominal/2.5-GB-free guard; A03 Core is unsupported for the translator. | Offering a checked bilingual phrase as text avoids loading the translator. Speaking it remains dependent on an installed target voice and device performance. |

## Four coherent features and acceptance criteria

| Feature | Real purpose and bounded behavior | Integration | Meaningful acceptance criteria |
| --- | --- | --- | --- |
| **1. Review before send** | Optional persistent review preference; on release display an editable source draft with original recognition retained. “Send” for a peer, “Translate” for Solo, and “Discard” clearly distinguish intent. Cancelling a press cancels capture rather than submitting. | New `Phase.Reviewing`, `SessionState.draft`, confirmation entry point; UI edits stay local until confirmation. Drafts must lock source language/context and prevent overlapping captures. | With review enabled, no packet, translator call or playback occurs before confirmation. Corrected text is what is transmitted/translated, while original recognition remains inspectable. Discard/cancel creates no outgoing message. Empty/oversize text is rejected without silent truncation. Normal review-off hold-to-talk behavior continues. |
| **2. Check important details before speech** | Display original and target text with explicit warnings for detectable numeric/time/format differences. Withhold automatic playback when warnings exist; offer “Play anyway” for that specific message. Never display a confidence percentage, “safe translation,” or a “verified” badge from these heuristics. | `Message.warnings: List<String>`, `Status.NEEDS_REVIEW`; central playback gate, not only an animated warning in Compose. Incoming text may still be acknowledged as delivered; that does not assert translation correctness. | Unicode digits, signs, decimals, time separators and repeated quantities have explicit fixtures. `-5` versus `5` and `1.5` versus `15` must not look equal. An unflagged “25, not 50” with swapped roles is explicitly outside the heuristic guarantee. Warning-bearing messages produce **zero audio until explicit action**. Replay also respects the gate; “Play anyway” is one-message permission, not a global bypass. |
| **3. Exact phrases reviewed by the user** | Save source/target language, exact source and editable exact target text; require a checkbox such as “I reviewed this translation.” Provide add/edit/remove and an empty state, with no fake multilingual seed data. Mark generated output as generated until a person accepts/edits it. Reuse an exact matching pair without NLLB, including before model installation or on an unsupported translator device. | Persistent phrase repository; reviewed-phrase translator wrapper matches source + source language + requested target language exactly and returns `TranslationOrigin.REVIEWED_PHRASE`. Phrasebook UI is available before the large model loads. Target voice remains optional: show readable text if missing. | Imported/current model not installed and `canLoad=false`: exact phrase text still works and NLLB is never called. Changed source wording, different target language or unreviewed entry does not silently match. Edit/delete survives restart and does not modify an in-flight snapshot. Manual target code points and punctuation are preserved. Voice lookup uses the saved target language and absent voice does not silently switch language. |
| **4. Type, retry and replay without starting over** | Type a phrase instead of recording; use the same draft/review and translation rules. Retry failed local translation after installing a model; replay retained translated text after adding a voice or when someone missed it. Preserve source and translated text. No silent original-language audio fallback. | Central typed submission and per-message retry/replay entry points; existing queue, speaker locks and duplicate protection are reused. UI states explain “sent text,” “translation failed,” “text only” and “needs review.” | Typed input needs no mic permission/STT call. Local retry changes the same history entry and does not resend an already delivered packet or re-run successful recognition. Replay of a translation uses retained text, not a new model output. No duplication on repeated taps or reconnect. Retry/Play buttons disable appropriately during queued/running work. Resource-ineligible users get exact-phrase/text alternatives, not a promise that typing fixes RAM. |

The exact-phrase fallback guarantees reuse of a stored string, not linguistic correctness. “User reviewed” means the user checked it; it does not imply certification by a native speaker. A person can still approve an incorrect phrase.

### Network phrase limitation that must remain visible

The existing packet carries recognized/source text and its source language, with recipient-side translation. Selecting a reviewed phrase on the sender **does not install its reviewed target on the peer**. For this phase, send the source wording and label that the recipient uses its own translation/phrasebook; use the exact reviewed target locally in Solo or when that receiving phone has the matching entry. Do not display an “exact translation sent” success claim. Sharing reviewed pairs or a new versioned bilingual wire format would be a separate feature, not something to imply in this implementation.

## Five defensible core differentiators

| Differentiator | What may be claimed after the relevant implementation/tests | Qualification |
| --- | --- | --- |
| **Focused ten-language Indian workflow** | Independent source/listening choices across Hindi, English, Marathi, Gujarati, Bengali, Tamil, Telugu, Kannada, Malayalam and Odia; model execution has smoke coverage of all 90 directed pairs. | Coverage is not natural-speech translation accuracy or a measured phone latency promise. RTranslator and Google also support multilingual translation. |
| **Local peer conversations over a text link** | Original recognized text travels over local Wi-Fi or Bluetooth; recipient runs translation and its installed voice without a conversation internet request. | RTranslator already uses local peer text translation over Bluetooth; Microsoft's current multi-device feature is retired. Our two-transport option is an implementation fact, not “world first.” |
| **Human control over source and important details** | Users can correct source text before sending, inspect source/target, and explicitly authorize playback when deterministic warnings fire. | Does not repair NLLB automatically or produce semantic confidence. The benefit is control and visible evidence. |
| **Resource-aware exact-phrase continuity** | A manually reviewed exact pair works as text without loading the large model; installed target voice can speak it. | This is a bounded fallback for stored phrases, not unrestricted offline translation on 2-GB phones. Voice speed on low-end devices remains a limitation. |
| **Recoverable, inspectable output with managed voices** | Typed entry, retained source/target, retry/replay, explicit missing-model/voice errors and independently installed native-script voice packs form one recoverable workflow. | Typing, replay and saved phrases are standard elsewhere; the differentiation is the coherent combination and transparent failure handling. Current phone validation remains pending. |

Avoid proposed distractors in this phase: OCR/camera, continuous listening, cloud fallback, accounts/social sharing, a medical “safe mode,” invented confidence scores, automatic semantic repair, or a claim of zero lag. None is needed to solve the identified source-control, detail, resource and recovery gaps.

## Accepted integration contract for the UI

Root/session agent supplied this contract; no code was written during this research:

- `Phase.Reviewing`; `SessionState.draft: SourceDraft?` with `text`, `originalText`, `langCode`, and `origin` (`InputOrigin.SPEECH` or `TYPED`); `reviewBeforeSend: Boolean`; `queuedMessages: Int`.
- Message additions: nullable `originalTranscript`, `inputOrigin`, `warnings: List<String>`, nullable `translationOrigin` (`MODEL` / `REVIEWED_PHRASE`), plus `Status.NEEDS_REVIEW`.
- ViewModel supplies phrasebook entries and error; shared entry type is `ReviewedPhrase`. UI must adapt to the exact repository type rather than create a parallel persistence schema.
- TalkScreen additional callbacks: `onPressCancel()`, `onSubmitText(String)`, `onSetReviewBeforeSend(Boolean)`, `onConfirmDraft(String)`, `onDiscardDraft()`, `onRetryMessage(Int)`, `onReplayMessage(Int, Boolean)`, `onSavePhrase(sourceIso, targetIso, sourceText, targetText)`, `onRemovePhrase(id)`, `onUsePhrase(ReviewedPhrase)`.
- Replay boolean is explicit one-message “Play anyway”; normal replay must pass `false` and retain the warning gate. Source confirmation accepts the edited text and central code performs validation.
- Phrase save editor prepopulates message source/target when available, allows manually supplied target text, and requires explicit “I reviewed this translation.” Never infer review merely because translation completed or somebody tapped Save.
- Planned UI ownership: `TalkScreen.kt`, `HoldToTalkButton.kt`, `SessionUi.kt`, and new Review/Phrasebook composables. Root owns MainScreen wiring and ViewModel. Preserve native-script fonts and keep recovery actions distinct from delivery and translation-success labels.

## Evidence and claim limits

No competitor-app hands-on usability, phone frame timing, real translation accuracy comparison, or current phone performance was measured here. No feature should be sold as globally exclusive. Microsoft's current offline status was not established because the official help pages were inaccessible; mention that uncertainty only in internal comparison, not as a fabricated competitive absence. RTranslator timing/RAM tables are its author's measurements with unrecorded matching hardware in our context and cannot be compared numerically against our cloud results.
